# Reveries protocol V1

`reveries/v1` is a Git-notes protocol for immutable engineering decisions. Its canonical notes
ref is `refs/notes/reveries`; callers must name that ref explicitly and must not change
`core.notesRef`.

## Object model

The three original record types are unchanged by any additive ticket:

- `reverie`, attached to a Git blob or (additively, RVR-013) tree;
- `session-summary`, attached to a Git commit;
- `reveries-init`, attached to the adoption commit.

Additive families extend that set without rewriting it: `transition-summary` and
`publication-attestation` (RVR-004/RVR-005), `correction`, `resolution`, and `redaction` (RVR-007),
`signature` (RVR-009), and `occurrence` and `lineage` (RVR-014).

A note body is UTF-8 JSONL. Each physical line is one complete canonical JSON object, and a note
is semantically an unordered set of records. The same ref carries every record type.

A reverie describes the driving event, selected decision and why it addresses that event, impact,
and recurrence control. It may additionally record meaningful alternatives and typed sources.
Notes are attributable evidence; they are neither authority nor proof of causality.

## Blob applicability

A blob reverie applies universally to every occurrence of that exact blob. A byte-identical copy,
an unchanged rename, and later reuse of an old blob all resolve the same evidence. An edit produces
a new blob and receives no decision silently. Paths may be sources or navigation aids, but are not
applicability metadata.

Before adding a reverie, authors must inspect the current paths resolving to the blob and decide
whether the decision holds for every one. Never make meaningless content changes merely to split
identity.

## Tree applicability (additive, RVR-013)

A reverie may also attach to a Git tree: the exact immutable subtree subject. Tree evidence
follows the same content-addressed rules as blob evidence, and the `rv:` identity is unchanged:
the same canonical record carries the same ID on either subject kind, so V1 blob history reads
unchanged. A byte-identical subtree at another path, an unchanged rename or copy, and later reuse
of the same tree all resolve the same evidence. A descendant edit produces a new ancestor tree and
receives no decision silently. The revision root tree reports the stable display path `.`.

Placement stays strict by annotated object type: blob notes carry reveries, occurrence records, and
the global fact families; tree notes carry reveries, occurrence records, and co-located result-tree
transition summaries; commit notes carry session summaries and lineage edges (never file reveries,
occurrence records, or transition records). A lineage edge attached to any commit other than the one
it names, and an occurrence record attached to any subject other than the one its coordinate names,
are refused. Session summaries and initialization records never attach to trees.

Retirement entries keep the wire key `from_blob` byte-for-byte for V1 compatibility; its value is
the annotated blob-or-tree predecessor subject.

## Occurrence applicability (additive, RVR-014)

Content identity is too coarse when one subject occurs in several places with different rationale:
a vendored copy, a hand-written original, and a fixture. An `occurrence` record states a decision
about exactly one occurrence, and is opt-in: universal reveries remain the default and are
unaffected.

- An occurrence is the coordinate `{commit, path, subject}` — a revision, a path inside it, and the
  exact blob or tree found there. `.` is the root tree.
- **The coordinate is part of the identity.** Two occurrences of one blob are two `oc:` records, so
  they may carry different rationale; identical prose at two coordinates is still two records.
- The record rides the note of `occurrence.subject`, and that subject must equal the annotated
  object. The note is therefore content-addressed while the evidence inside it is not.
- At `occurrence.commit`, `occurrence.path` must hold exactly `occurrence.subject`. A coordinate
  the repository cannot resolve fails validation.
- An occurrence never applies universally. Reporting shows occurrences applicable to the occurrence
  on screen — the anchor itself, or one explicit lineage edge away — separately from occurrences
  anchored elsewhere, which are shown with their own coordinate. A shared object ID is never a
  reason to present one path's rationale as another's.
- An occurrence record carries no supersession edge of its own. A mistaken one is corrected through
  the ordinary `correction` and `resolution` records, which may name `oc:` and `lg:` heads, and is
  hidden by a `redaction` targeting one. A conflicting identity fails closed.

## Lineage edges (additive, RVR-014)

A `lineage` record is an explicit, durable pairing between occurrences, bound to one direct parent
and one result commit. It exists because a rename-plus-edit, a split, a join, or an extraction has
no same-path successor, and guessing one is how a decision gets stranded or wrongly inherited.

- Fields: `kind`, `parent`, `commit`, `from`, `to`, an optional `transition` link to the RVR-004
  tree transition, and the usual causal fields. Endpoints are `{path, subject}`; `from` resolves in
  `parent` and `to` in `commit`.
- Kinds and their declared shape: `preserve` 1:1, `split` 1:N, `merge` N:1, `derive` N:M with N ≥ 1
  and M ≥ 1 (the general case, including 2:3), `retire` 1:0. `from` is always nonempty; `to` is empty
  only for `retire`. The N-to-M generality is bounded like every other dimension: `maxLineageRefs`
  caps the endpoints on one edge, so a wide relation stays a bounded fact.
- The record rides the note of `commit`, beside that commit's session summary, and is refused
  anywhere else. `parent` must be a direct parent of `commit`; every endpoint must resolve in the
  revision it names; every `from` subject must carry evidence, because pairing an unannotated subject
  would relate decisions that do not exist. Recording additionally refuses what the check could
  never authorize: every `from` occurrence must be disturbed by exactly this parent→commit change,
  and every `to` occurrence present in its result. An unchanged move or copy needs no edge — the
  same subject is still reachable — so claiming one is refused at record time rather than failing
  later as contradictory.
- Endpoints are sorted by `(path, subject)` before hashing, so the order an author lists them in
  cannot change the ID.
- **An edge discharges nothing.** It states which subjects are related and why. For every active
  decision on a predecessor, each successor still needs its own continuation, supersession, or a
  causal retirement. A split or merge edge generates per-endpoint obligations rather than one
  verdict about the set.
- A predecessor's successor set comes from exactly one source: RVR-013 same-path identity pairing, or
  one authoritative edge. Two claims for one predecessor fail closed even when they name the same
  subjects — agreeing by accident is not an agreement anyone asserted — while repeating one record is
  idempotence. An empty set is not a claim, so an identity pair with no successor still accepts one
  edge.

### Authority, and history

For a check of commit `C` against parent `P`, each edge is classified:

- **authoritative** — the edge names exactly `C` and `P`, every `from` coordinate is a coordinate
  this change disturbs, and every `to` coordinate is present in `C`. Matching is on the whole
  coordinate, not the object ID: the same subject at another path is a different occurrence.
- **history** — the edge describes another change. It drives `history`, `show`, and `search`, and
  never a continuity verdict.
- **contradictory** — the edge claims `C` and `P` while naming an endpoint that is not part of that
  change. Strict operations refuse it.

Path history follows every edge backwards from the coordinate on screen, which is how a
rename-plus-edit keeps its evidence trail.

### Similarity is never authority

Git similarity detection may propose. It never decides: the authoritative transition matcher reads
raw diffs with rename detection off, so a renamed-and-edited subject has no successor until a person
records an edge and a per-decision disposition. `reveries lineage suggest` reports candidates as
unconfirmed suggestions and nothing else consumes them. Language adapters may propose symbol
relationships on the same terms.

## Records and schemas

The normative machine-readable structures are:

- [reverie.schema.json](schemas/reverie.schema.json)
- [occurrence.schema.json](schemas/occurrence.schema.json)
- [lineage.schema.json](schemas/lineage.schema.json)
- [session-summary.schema.json](schemas/session-summary.schema.json)
- [reveries-init.schema.json](schemas/reveries-init.schema.json)

Every record has `v: 1`. Unknown versions and types fail strict operations. A tolerant reader
retains valid records and reports malformed lines; a strict reader refuses damaged notes for
writes, continuity, publication, automatic delivery, and doctor checks.

### Reverie fields

All fields are present; only `session` may be `null`.

| Field | Rule |
| --- | --- |
| `id` | `rv:` plus the full repository-format object ID derived from semantic content. |
| `driving_event` | Nonempty concrete forcing condition, not a task label. |
| `decision` | Nonempty selected action and why it addresses the event. |
| `impact` | Nonempty consequence beyond changed lines. |
| `recurrence_control` | String describing prevention/detection or `null`; no placeholders. |
| `alternatives` | Meaningful rejected alternatives only. |
| `sources` | Typed, ordered source assertions; may be empty. |
| `supersedes` | Full reverie IDs; may be empty. |
| `author_email` | Required Git email identity. |
| `created_at` | UTC RFC 3339 timestamp. |

`author_email`, `session`, and `created_at` are attestations, not identity. A changed causal
statement receives a new reverie that supersedes the inaccurate predecessor; an existing reverie
is never edited under the same ID.

### Session summaries

Every initialization commit and every published descendant has exactly one effective
`session-summary` on its commit object. Its identity is the full annotated commit ID. `entries`
is nonempty and preserves authored order. Each entry has causal fields, `alternatives`,
`sources`, `reveries`, and `retirements`.

`reveries` lists new decisions and material supersessions, not ordinary continuations. A
retirement is `{reverie, from_blob, reason}` and has a specific causal reason. A correction may
add `correction_reason`; it replaces the current effective summary while the notes-ref history
retains the earlier evidence. Concurrent distinct summaries on one commit are a strict conflict.

Merge commits and automated commits still require causal summaries. Rewrites create new commits,
so amend, rebase, squash, and cherry-pick require fresh summaries rather than copied explanations.

### Initialization records

The adoption commit has one summary plus one `reveries-init`. The record establishes protocol
version, canonical notes ref, historical publishing remotes/hosts, and the grandfathering
boundary. It does not override current local configuration. Initializers prepare tracked changes
and print follow-up commands; they do not create the adoption commit unless explicitly asked.

## Canonical JSONL

Authoritative records obey all of these byte rules:

1. UTF-8, without a BOM or literal control bytes.
2. One object per physical line, no insignificant whitespace, exactly one trailing LF per record.
3. Keys in protocol-defined order; string outer whitespace trimmed; internal whitespace preserved.
4. No Unicode normalization beyond valid JSON encoding.
5. `alternatives` sort by UTF-8 byte order; `supersedes` and `reveries` sort lexically.
6. `sources` sort by `(relation, kind, ref, at)`; `retirements` sort by `(reverie, from_blob)`.
7. `entries` retain authored order.

Record order in a note has no semantic meaning. `cat_sort_uniq` can mechanically merge canonical
lines, but it cannot resolve duplicate semantic identities, summary conflicts, forks, or cycles.

### Defined key order

Reverie:

```text
v, type, id, driving_event, decision, impact, recurrence_control, alternatives,
sources, supersedes, author_email, session, created_at
```

Session summary:

```text
v, type, author_email, session, created_at, entries, correction_reason
```

Summary entry:

```text
driving_event, decision, impact, recurrence_control, alternatives, sources,
reveries, retirements
```

Initialization record:

```text
v, type, protocol, notes_ref, publishing_remotes, hosts, author_email, created_at
```

Occurrence record:

```text
v, type, id, occurrence, driving_event, decision, impact, recurrence_control, alternatives,
sources, author_email, session, created_at
```

Lineage record:

```text
v, type, id, kind, parent, commit, from, to, transition, driving_event, decision, impact,
recurrence_control, alternatives, sources, author_email, session, created_at
```

## Semantic identity

A reverie ID is derived only from this canonical, LF-terminated semantic payload:

```text
v, driving_event, decision, impact, recurrence_control, alternatives, sources, supersedes
```

Hash it through the repository’s Git object algorithm:

```bash
oid="$(printf '%s\n' "$semantic" | git hash-object --stdin)"
id="rv:$oid"
```

An occurrence ID hashes the same causal payload plus its coordinate, and a lineage ID hashes its
kind, the bound parent and commit, both sorted endpoint sets, the optional transition link, and the
causal payload. Author metadata is excluded in both, so an amend keeps the identity. The concrete
bytes are:

```text
occurrence: v, type, occurrence, driving_event, decision, impact, recurrence_control,
            alternatives, sources
lineage:    v, type, kind, parent, commit, from, to, transition, driving_event, decision,
            impact, recurrence_control, alternatives, sources
```

This supports SHA-1 and SHA-256 repositories. Same ID/same semantic payload is one decision;
tolerant readers may retain distinct attestations, while strict projection counts it once. Same
ID/different semantic payload is corruption.

## Sources

Valid kinds are `commit`, `blob`, `tree`, `path`, `note`, `git-email`, and `issue`
(V1 defined all but `tree`; RVR-013 adds `tree` as an additive provenance kind).
Valid relations are
`caused-by`, `constrained-by`, `requested-by`, `derived-from`, `implements`, and
`corroborated-by`. A tree source must
reference an existing tree object, exactly like a blob source.

Local commits, blobs, and trees must exist; a path must resolve at its required `at` commit; a `note`
source must reference an existing reverie. Occurrence and lineage identities are referenced through
corrections, resolutions, and redactions, not through `note` sources, because automatic delivery
resolves a `note` source against reveries only. Issues and Git emails are syntactically checked only.
Issue examples include `github:owner/repository#417`, `gitlab:group/project#417`,
`linear:ENG-417`, `jira:PROJ-417`, and `generic:tracker:417`.

## Active projection and continuity

For a blob, read valid reveries, collapse identical semantic IDs, construct the supersession graph,
mark superseded records historical, and expose its terminal records as active. Strict operations
refuse a supersession cycle, an unresolved fork that reaches one blob, a conflicting duplicate ID,
or damaged input.

For each active reverie on every annotated predecessor blob changed by a commit, choose exactly
one disposition:

- **Continue:** copy the exact canonical record and ID onto the successor blob.
- **Supersede:** attach a new causal reverie on the successor whose `supersedes` names the old ID.
- **Retire:** add a causal retirement to the new commit’s session-summary entry.

Pure renames and byte-identical copies need no disposition. An ambiguous rename-plus-edit or a
delete-plus-add is never guessed: supply an explicit successor. For deletion without a successor,
retire every active predecessor decision. A merge evaluates this independently for each parent.

For an annotated predecessor tree changed by a commit, the same three dispositions apply, and the
successor set comes from exactly one source: same-path identity, or one authoritative lineage edge.
Identical directory paths pair; pairing is never inferred from similarity, from Git rename
detection, or from matching records on an unrelated reachable tree. A vanished subtree path — a
rename-plus-edit, a split, a join — is resolved by an explicit edge plus a per-decision disposition,
or by a causal retirement. Two claims for one predecessor fail closed.

Per successor, exactly one disposition is required. Continuation means the same reverie ID is present
on **every** successor of the pairing; a supersession means a successor names the decision in
`supersedes`. An endpoint with neither, or with both, is an obligation naming that endpoint, so one
successor's evidence can never discharge another. A retirement is the single global alternative and
is refused when a successor still carries the decision or its replacement.

## Publishing and synchronization

Before substantial shared work, explicitly pull notes or state that local notes may be stale.
Automatic delivery never accesses the network. For an approved remote, fetch into a remote-tracking
ref, merge with `cat_sort_uniq` into a private candidate, validate the complete candidate snapshot,
and compare-and-swap it into the canonical ref only after validation succeeds.

```bash
git fetch origin '+refs/notes/reveries*:refs/notes/remotes/origin/reveries*'
git notes --ref=refs/notes/reveries-txn/<candidate> merge -s cat_sort_uniq \
  refs/notes/remotes/origin/reveries
```

Use `reveries push origin` for publication. It performs a dry-run atomic capability check,
then requests the branch and notes ref in one atomic transaction and refuses a receiver that does
not support atomic pushes. If the helper is unavailable, push the notes ref first and push the code
ref second with an explicit `--no-verify` bypass. This is a lower-grade fallback. Never use a
generic multi-ref push.

If validation fails, the canonical notes tip remains unchanged and the candidate is preserved at
`refs/reveries/quarantine/<remote>/<oid>`. The quarantined note commit retains both source records
so a later resolver can produce a valid replacement candidate.

The helper publishes local notes writes with a compare-and-swap guard on `refs/notes/reveries`
instead of a lock; a lost race retries from the new tip with bounded backoff and then fails with a
contention error. Linked worktrees share the same refs. A pre-push hook is client-side only and may
be bypassed. It checks notes inclusion, summary coverage, continuity, current notes
state, remote incorporation, and unresolved semantic conflicts; it cannot add a missing refspec or
prove receive-side enforcement. Local hooks are not a security boundary.

## Security and failure rules

Strict automatic delivery validates the schema, rejects unknown types, strips control characters,
bounds fields, labels records as repository evidence, and injects only complete records. It never
executes note content or places it under an instructions heading.

When notes are malformed, merge-conflicted, shallow, absent remotely, or successor mapping is
ambiguous, raw inspection remains available but strict mutation and publication must refuse when
they cannot establish completeness. Normal removal deletes only integration/configuration and
preserves local and remote evidence. Protocol migration creates a new notes ref when V1 semantics
cannot be preserved safely.
