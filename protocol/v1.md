# Reveries protocol V1

`reveries/v1` is a Git-notes protocol for immutable engineering decisions. Its canonical notes
ref is `refs/notes/reveries`; callers must name that ref explicitly and must not change
`core.notesRef`.

The authoritative state is Git objects plus `refs/notes/reveries` plus
`refs/reveries/retention`. Nothing else is required.

## Object model

The lean core defines two record types:

- `reverie`, attached to a Git blob, a Git tree, or an exact region of a blob;
- `lineage`, an explicit relation between predecessor and successor subjects.

A note body is UTF-8 JSONL. Each physical line is one complete canonical JSON object, and a
note is semantically an unordered set of records. The same ref carries every record type.

A reverie describes the driving event, the selected decision and why it addresses that event,
the impact, and a recurrence control (or none). It may record meaningful alternatives, typed
sources, and superseded predecessor IDs.

A reader validates the lean record types and **skips unknown record types without interpreting
or rejecting them**. A note written by another version, or by a removed feature, keeps its
bytes and is counted by `doctor`; it is never damage by itself.

## Canonical JSONL

- One JSON object per line, compact (no insignificant whitespace), UTF-8, one trailing LF.
- Keys appear in protocol order.
- `alternatives` sort by UTF-8 byte order; `supersedes` sort lexically; `sources` sort by
  `(relation, kind, ref, at)`.
- Array order that carries meaning (such as lineage endpoints) is defined by the record type,
  not by insertion order.

`reveries doctor` validates the notes ref. Tolerant parsing preserves valid records and reports
malformed lines so an operator can inspect damage without losing the rest of the note.

## Identity

A record ID is the repository object hash of the canonical semantic payload with the type
prefix:

| Record | ID | Payload |
| --- | --- | --- |
| `reverie` | `rv:<hash>` | the semantic fields in protocol order |
| `lineage` | `lg:<hash>` | the lineage semantic fields in protocol order |

The ID covers only the causal semantic payload. Metadata such as `author_email`, `session`, and
`created_at` does not participate, so the same decision has one identity regardless of who
recorded it. The object format follows the repository: SHA-1 is 40 hex characters, SHA-256 is
64.

Do not edit causal content under an existing ID. A changed rationale is a new reverie that
names the old ID in `supersedes`.

## Blob and tree applicability

A blob or tree reverie applies universally to every occurrence of that exact object. A
byte-identical copy, an unchanged rename, and later reuse of an old object all resolve the same
evidence. An edit produces a new object and receives no decision silently.

Paths are navigation aids and sources, never applicability metadata. Before adding a reverie,
inspect the current paths resolving to the object and decide whether the decision holds for
every one.

## Region applicability

A reverie may attach to an exact region of a blob instead of the whole blob. The `region`
descriptor carries:

```json
{
  "kind": "region",
  "blob": "<blob object id>",
  "exact_hash": "<object hash of the selected bytes>",
  "start_line_hint": 10,
  "end_line_hint": 24,
  "prefix_hint": "<first selected line>",
  "suffix_hint": "<last selected line>"
}
```

Identity is the blob plus `exact_hash`. The line numbers and the prefix/suffix strings are
navigation hints only; moving the region without changing its bytes does not change the
record ID. Editing the selected bytes leaves the old evidence on the old blob and gives the new
blob no evidence.

## Lineage

A `lineage` record pairs a `from` endpoint resolved in `parent` with a `to` endpoint resolved
in `commit`, both direct Git relations:

| Kind | Shape | Meaning |
| --- | --- | --- |
| `preserve` | 1 to 1 | The same intent moved to a new subject. |
| `split` | 1 to N | One subject became several. |
| `merge` | N to 1 | Several subjects became one. |
| `derive` | N to M | The general case, including 2 to 3. |
| `retire` | 1 to 0 | The occurrence ended with no successor. |

Endpoints are `{path, subject}` objects, where `subject` is the object ID found at `path` in the
named revision. Because endpoints are object IDs, an edge survives a rebase. The immutable
record is written to the note of every `to` endpoint, or to every `from` endpoint when `to` is
empty, so the edge is discoverable from either end.

A lineage record also carries a `transition` field. The lean core has no transitions, so a
writer always emits `transition: null`. The field is reserved and kept in the payload because
the lineage identity hashes it: dropping it would change the `lg:` ID of every edge recorded
before the lean core. It carries no lean-core meaning.

Lineage is never inferred. A similarity suggestion is not evidence until it is recorded. An
edge carries no decision: every decision on a predecessor still needs its own continuation on
each successor, a supersession, or a retirement.

## Notes union

Two clones combine their notes refs with Git's `cat_sort_uniq` merge strategy. The union is a
pure set union of canonical lines, so it is deterministic and idempotent. A record that appears
on both sides is not duplicated. Two records that claim one ID with different semantic content
are damage, not a union: the merge is refused where it would introduce that conflict, and
`reveries doctor` reports it. A record type this build does not know is not a conflict; it is
preserved and skipped.

## Retention

`refs/reveries/retention` anchors annotated objects so a pruning `git gc` keeps them reachable.
The configured policy (`reveries.retention`) is one of `none`, `active`, `all`, or `archive`;
`active` is the default. The ref is a deterministic function of the selected subjects and is
safe to rebuild at any time with `reveries retain`.

## Publication

Publish with an ordinary `git push` of `refs/notes/reveries`. `reveries push <remote>` only adds
a single atomic transaction over HEAD and the notes ref. Nothing in the protocol requires a
hook, a workflow, or a server.

## Migration

`reveries migrate` converts legacy records into lean evidence where the subject is unambiguous,
and reports what it leaves historical. It never deletes bytes: legacy records stay in their
notes, are preserved by the tolerant reader, and are only appended to. The command is
idempotent and safe to rerun.

| Legacy record | Conversion |
| --- | --- |
| `reverie`, `lineage` | Already lean; counted, unchanged. |
| `session-summary` on a blob or tree | Each causal entry becomes a `reverie` on that exact object. |
| `transition-summary` on a tree | The causal content becomes a `reverie` on the result tree. |
| A retirement with a resolvable subject | A `retire` lineage edge bound to the summary's commit. |
| `session-summary` on a commit | Its narration names no exact content subject, so it stays historical and is reported as unconverted. |
| `reveries-init` | Kept as configuration; never creates an adoption boundary. |

The migration does not reinterpret commit narration onto a commit or a tree it never named. An
unconverted record is a valid outcome, not a failure: the rationale is still readable.

## Removed record types

Earlier versions defined `session-summary`, `reveries-init`, `transition-summary`,
`publication-attestation`, `correction`, `resolution`, `redaction`, `signature`, and
`occurrence`, and a `confidential-pointer` source kind. The lean core does not define or
interpret them. Their bytes remain readable in the notes and are skipped, so existing evidence
is never destroyed by an upgrade.

Legacy bytes are never damage by themselves. A note that carries a record type this build does
not know still validates, still accepts new records, and still merges; `doctor` counts the
legacy records as a notice. `reveries migrate` converts the legacy records whose subject is
unambiguous into `reverie` or `lineage` evidence and reports the rest. Writers emit only the
lean record types.
